# fanmark.id ピボット・ロードマップ — ライバー市場への再ポジショニング

> **このドキュメントの目的**: fanmark.id を「絵文字ドメインレジストリ」から「**ライブ配信文化圏(TikTok Live 等)の公式ファンマ登録所**」へ再ポジショニングするための、検証ゲート付きロードマップ。
> 各フェーズに「進む/止まる」の判断基準(Gate)を置き、**建築より検証を先行**させる。
>
> **作成日**: 2026-07-09
> **関連**: `docs/REFACTORING_PLAN.md`(技術的リファクタリング計画。本ロードマップとの優先順位関係は §7 参照)

---

## 1. 再ポジショニングの骨子

### 1.1 新しい一文定義

> **fanmark.id は、ライバーの「ファンマ」を本人確認付きで登録し、ファンマひとつでライバーに辿り着けるようにする公式登録所。**

### 1.2 なぜこの市場か(意思決定の根拠)

| 論点 | 一般ファン向け(現状) | ライバー市場(本ロードマップ) |
|---|---|---|
| 絵文字を「打つ・覚える」行動 | 存在しない(装飾のみ) | **毎日存在する**(リスナーは推しのファンマを名前に入れ、コメントで打つ) |
| 一意性(独占)への需要 | 弱い | **実在する**(ファンマ被りはライバーの実際の悩み。「先に宣言して押さえたい」) |
| 逆引きニーズ | ない | **ある**(野良で見たファンマから推しを探す手段がプラットフォーム内にない) |
| 支払者 | 個人(無料代替が強い) | ライバー本人+**ライバー事務所(B2B2C)** |
| 既存実装との距離 | — | **最短**(登録・正規化・プロフィール・移管・お気に入りがほぼ流用可能) |
| 名前との整合 | 弱い | **「ファンマ」+「ID」= サービス名そのもの** |

### 1.3 このピボットの最大の設計原則

**レジストリの権威は技術ではなく社会的合意である。**
大手ライバーのファンマを無関係な第三者が先取りできる仕様は、コミュニティの信頼を一発で失う。よって:

- **本人確認(TikTokアカウント紐付け)を登録の中核に置く**。「fanmark.id に載っている = 本人が登録した」を成立させる。
- 先着順の一般開放は本人確認の仕組みが安定するまで行わない。
- スクワッティング(取得放置)対策として、既存のライセンス期限機構を「活動実態のない登録の自然解放」として再利用する。

## 2. フェーズ全体像

```
P0 検証(2〜4週・コードほぼ書かない)
 └─ Gate G1: 課題の実在確認
P1 再ポジショニングMVP(4〜6週・既存資産の組み替え中心)
 └─ Gate G2: ライバー本人の登録・利用
P2 コミュニティ浸透・事務所B2B(8〜12週)
 └─ Gate G3: 事務所パイロットの継続意思
P3 収益化・他プラットフォーム展開
```

各Gateを通過しなければ次に進まない。**Gateで止まる判断も成功**(最小コストで誤った方向を棄却できたことになる)。

## 3. Phase P0: 検証(2〜4週間)

**目的**: 「ファンマ被り」「逆引き」「公式登録」に対する需要が実在するかを、開発ゼロで確かめる。

### P0-1. カスタマーインタビュー

- 対象: ライバー10名+リスナー10名(TikTok Live 中心。可能なら中堅〜マイクロ規模のライバーを優先。大手は事務所経由でないと届かないため)。
- 聞くこと(仮説を売り込まない。過去の事実だけ聞く):
  - ライバー: ファンマをどう決めたか / 被りに気づいたことは / そのとき何をしたか / lit.link等のリンクハブは何を使っているか / 「公式に登録できる」と聞いて最初に思うことは
  - リスナー: 推しのファンマをいくつ覚えているか / 野良で見かけたファンマから配信者を探したくなった経験は / そのときどうしたか
- 記録: 発言の生ログを残し、「被り」「逆引き」「証明」の3課題ごとに頻度を集計する。

### P0-2. LPスモークテスト

- 既存の `waitlist` テーブルと招待制インフラ(`invitation_codes`, `system_settings.invitation_mode`)を**そのまま流用**し、新コピーのLPを1枚作る:
  - 見出し例: 「あなたのファンマ、先に登録しませんか — ライバーのための公式ファンマ登録所」
  - CTA: ウェイトリスト登録(TikTokアカウント名も任意入力してもらう → ライバー比率の測定になる)
- 流通: ライバー系ハッシュタグでの告知、知人ライバーへの直接依頼、可能なら少額のSNS広告。
- 計測: LP訪問→ウェイトリスト転換率、登録者のライバー/リスナー比率。

### P0-3. 競合・文脈の確認

- TikTok本体のファンクラブ/バッジ機能の現状と、ファンマ文化への影響を整理。
- lit.link 等リンクハブのライバー利用実態。
- 他の配信アプリ(Pococha, 17LIVE, IRIAM, ふわっち)のファンマ文化の有無を確認 → **文化がクロスプラットフォームであるほど、TikTok依存リスクが下がる**(P3の展開先の根拠にもなる)。

### ✅ Gate G1(P1へ進む条件)

以下の**2つ以上**を満たすこと:

- [ ] インタビューでライバーの過半が「被り」または「公式に押さえたい」を自発的に語った
- [ ] リスナーの過半が「逆引きしたい経験」を具体的エピソードで語った
- [ ] LP転換率が有意(目安: 訪問→登録 5%以上)かつライバー登録が10件以上

満たさない場合: ピボット中止または再設計。既存サービスは現状維持のまま、`REFACTORING_PLAN.md` の Phase 0-1 のみ実施して保守モードへ。

## 4. Phase P1: 再ポジショニングMVP(4〜6週間)

**目的**: 「本人確認付きファンマ登録 → ファンマで辿り着けるページ」の最小ループを、既存資産の組み替えで成立させる。

### P1-1. 新規開発: TikTokアカウント本人確認 ★このフェーズの本丸

- フロー(API非依存の設計。TikTokに配信者向け公開APIがない前提で、規約違反となるスクレイピングを避ける):
  1. 登録時にTikTokプロフィールURLを入力
  2. ワンタイム確認コード(例: `fm-x7k2`)を発行し、「TikTokのbioにこのコードを一時的に記載してください」と案内
  3. 確認は当面**運営の手動確認**(管理画面に確認キューを作る)。自動化(oEmbed/公式API)は量が増えてから検討
  4. 確認完了で「✓本人確認済み」バッジをファンマページに表示
- データ: `user_settings` に `tiktok_url` / `verification_status` / `verified_at` を追加(マイグレーション)。
- 管理画面: 既存 `AdminUserManagement` のパターンを流用し、確認キュー画面を追加。

### P1-2. 既存資産の組み替え(開発コスト小)

| 既存機能 | 扱い | 変更内容 |
|---|---|---|
| 登録・正規化エンジン | **中核として維持** | 変更なし(最重要資産) |
| プロフィール型アクセス (`profile`) | **主役化** | ライバー向けにテンプレ調整: TikTokライブへのリンクを最上部固定、ファンマバッジを大きく |
| redirect型アクセス | 維持 | 「配信ページへ直行」用途 |
| 検索(逆引き) | **主役化** | トップページの主導線を「ファンマを打って探す」に変更 |
| お気に入り | 維持・強化 | リスナー側の「推しのファンマを登録しておく」機能として再文脈化 |
| 移管(AuthCode) | 維持 | 「ファンマの引き継ぎ・譲渡」として文化に整合。UIの文言のみ変更 |
| ライセンス期限 | **大幅緩和** | S=7日等の短期失効を廃止し、全ティア「1年・無料、活動確認で更新」に統一。期限機構はスクワッティング対策としてのみ機能させる |
| 抽選 | **凍結(非表示)** | 失効が稀になるため出番がない。コードは残しUIから隠す |
| ティア課金・延長課金 | **凍結** | P1では全機能無料(成長優先)。Stripe連携はコードごと温存 |
| 招待制 | 活用 | P0のウェイトリストから招待コードで段階開放(本人確認の運用負荷制御を兼ねる) |

### P1-3. 見た目とメッセージの刷新

- LPをライバー向けに全面書き換え(P0-2のLPを本番化)。日本語優先、英語は追従。
- OGPカード(`generate-ogp-image`)を「✓本人確認済みファンマ証明カード」としてデザイン更新 → **ライバーが自分で告知に使いたくなる画像**にする(配布の武器)。

### ✅ Gate G2(P2へ進む条件)

- [ ] 本人確認済みライバーの登録が **30件以上**
- [ ] うち **半数以上がTikTokのbioまたは固定コメントに fanmark.id のリンクを実際に掲載**した(=本人が価値を認めた行動)
- [ ] ファンマ検索(逆引き)の実行数が週次で増加傾向

## 5. Phase P2: コミュニティ浸透・事務所B2B(8〜12週間)

**目的**: 個別ライバーの点を、事務所経由の面に変える。

### P2-1. ライバー事務所パイロット(1社)

- 提案パッケージ: 「所属ライバー全員の公式ファンマ登録+本人確認+リンクページ一式」を無償パイロットで提供。
- 必要開発:
  - **事務所ダッシュボード**: 所属ライバーの一括登録・一括本人確認・一覧管理(既存Admin系のCRUDパターンを流用)
  - 事務所公式バッジ(「〇〇事務所 所属」表示)
- パイロットの合意指標を事前に握る: 掲載率、リスナーからのアクセス数、事務所側の工数。

### P2-2. リスナー側の体験強化

- 「推しのファンマを名乗る」: リスナーが自分のプロフィールに推しファンマを表示(お気に入り機能の発展)。
- ファンマ証明カードのリスナー版(「私は🐰🌙のリスナーです」シェア画像)→ リスナーの告知がライバーの宣伝になる循環を作る。

### P2-3. 紛争・スクワッティングポリシーの明文化

- 「本人確認済みライバーからの異議申立て」フローを規約と運用に定義(商標紛争処理の簡易版)。
- 活動実態のない登録の期限失効ルールを公開ポリシー化。

### ✅ Gate G3(P3へ進む条件)

- [ ] パイロット事務所が**継続利用(または有償化への前向き回答)**を表明
- [ ] 登録ライバー100件以上、うち事務所経由が3割以上
- [ ] リスナー側の週次アクティブ(検索・お気に入り・カード生成のいずれか)が登録ライバー数の5倍以上

---

## 6. Phase P3: 収益化・展開(G3通過後に詳細化)

方向性のみ列挙(詳細計画はG3通過後に作る。**今作り込まない**こと自体が本ロードマップの方針):

- **事務所プラン(B2B・主力想定)**: 一括管理・公式バッジ・分析(ファンマ経由アクセス解析)の月額。
- **ライバー個人プレミアム**: ページテーマ、詳細分析、複数ファンマ。凍結中のStripe資産を再稼働。
- **他プラットフォーム展開**: Pococha / 17LIVE / IRIAM 等へ本人確認を拡張(P0-3の調査結果に基づく)。ファンマ文化がクロスプラットフォームであることが、TikTok依存リスクの保険になる。
- 物理グッズ(ファンマ入りQRアクキー等)は文化との親和性が高いが、在庫リスクがあるため提携で試す。

## 7. リファクタリング計画(REFACTORING_PLAN.md)との優先順位

ピボットの意思決定が仕様を動かすため、リファクタリングは以下に組み替える:

| リファクタリングPhase | 扱い | 理由 |
|---|---|---|
| Phase 0(安全網: CI・テスト) | **即時実施** | どの未来でも無駄にならない |
| Phase 1(デッドコード削除) | **即時実施** | 同上。ピボットでさらに増える削除対象の下地になる |
| Phase 3(バンドル最適化) | P1と並行で実施推奨 | 公開ページ(ファンマページ)の初速はどの構想でも生命線 |
| Phase 2(重複統合) | 任意 | 低リスクだが優先度は下がる |
| Phase 4〜7(データ層統一・共通化・分割・strict化) | **P0〜P1の間は凍結** | 「今の仕様を維持する」前提の投資。G2通過後、残す機能が確定してから対象を絞って再開 |

特に: 抽選・課金系のEdge Functionsに対するリファクタリング投資は、本ロードマップでは凍結対象の機能なので**行わない**。

## 8. リスク台帳(正直に)

| リスク | 深刻度 | 備え |
|---|---|---|
| TikTokが公式ファンマ機能を実装する | 高 | クロスプラットフォーム展開(P3)を保険に。事務所との関係資産はTikTok外でも有効 |
| レジストリの権威が確立しない(「登録して何?」で止まる) | 高 | G2の「bio掲載率」を正直に測る。掲載されないなら価値仮説が誤り |
| 本人確認の運用負荷(手動確認のスケール限界) | 中 | 招待制で流量を制御。100件/週を超えたら自動化に投資 |
| 大手ライバーのファンマを巡る紛争 | 中 | P2-3のポリシー先行整備。初期は招待制で先着開放しない |
| TikTok規約(bio確認手順の位置づけ) | 低〜中 | スクレイピング・API非依存の設計を維持。ユーザー自身による掲載・自己申告ベース |
| P0で需要が確認できない | — | それは成功(最小コストでの棄却)。保守モードへ移行 |

## 9. 直近2週間のアクション(具体)

1. インタビュー設計書を作り、ライバー/リスナー各10名のリクルートを開始(知人経由+配信コメント経由)
2. P0用LPのコピーを書き、既存waitlist基盤で公開
3. `REFACTORING_PLAN.md` Phase 0(CI+スモークテスト)を着手 — 検証と並行して進められる唯一の開発タスク
4. 他配信アプリのファンマ文化調査(P0-3)をデスクリサーチで完了

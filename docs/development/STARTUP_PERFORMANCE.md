## 直列待ちの解消

- カタログはアプリ表示と並行して取得する。従来の8ページ直列取得は、初回の版確定＋残り最大3ページずつの取得になる。
  3,944件・500件/ページの場合は8回の逐次応答待ちから4段階になる。実通信時間の半減保証ではない。
- 認証sessionとメンテナンス確認を並行して開始する。両方が確定するまで保護された画面を開かない。
- 表示だけの絵文字分割はUnicode graphemeを使い、カタログ・UUID変換を待たない。

## 待機中の操作と確認

実Worker・合成Auth・分割local D1/R2と実Chromeで以下を確認する。
カタログ/sessionの保留・catalog 503・module取得失敗だけを試験用に注入し、成功応答は実local Workerから取得する。

- sessionを保留している間にmaintenanceの応答が完了する。routeの操作画面はまだ開かない。
- カタログ応答0件のままトップの閲覧・入力開始ができ、全画面のカタログ待機は出ない。
- 入力確定時だけ待機を表示。入力と表示位置を保持し、取り消した確定は取得後に再実行しない。
- カタログ取得失敗→再試行で入力を保持し、同じページから実検索へ進める。
- 絵文字URLでカタログが取得できない場合、未対応/not-foundやトップ移動と誤判定しない。
- 遅延moduleの取得失敗を表示し、再読み込み後の管理画面は未認証ならログイン画面になる。
- 4言語×320/375/390/430px、5絵文字・dialog・picker、取得・保存・本人切替の回帰を維持する。

根拠は`npm run verify:app`、`npm run test:local`、正規production buildとPR/main CI。
localの計測は意図的に応答を保留しており、本番LCP/CLSや実端末・低速回線の実測として扱わない。
